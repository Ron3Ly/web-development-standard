## 0. 法的位置づけ・適用法令を区別する

| 根拠・ルール | 何を確認するか | 性質 |
| --- | --- | --- |
| 個人情報保護法（APPI） | 利用目的の特定・通知/公表、個人データの管理、第三者・外国への提供、保有個人データに関する公表等・開示等請求 | **適用される法的義務** |
| 電気通信事業法の外部送信規律 | 事業者・役務の適用範囲、外部送信される利用者情報・送信先・利用目的と所定の通知/公表等 | **該当する役務・情報送信で適用** |
| Google API Services / OAuthの規約 | Googleユーザーデータのアクセス・利用・保存・共有の説明、公開URL・審査条件など | **採用するサービスの契約/ポリシー** |
| Google Analytics利用規約 | GA4の利用明示、Cookieや識別子、Googleによる収集/処理の説明等 | **GA4を利用する場合の規約** |
| GDPRその他の海外法 | 法的根拠、保存期間、権利、移転等を含む通知義務 | **対象地域・事業実態次第** |
| 明瞭な日本語、短い見出し、履歴、UIからのリンク | 利用者が理解できる文書設計・継続管理 | **このリポジトリで採用する品質標準** |

**重要:** 個人情報保護委員会（PPC）は「プライバシーポリシーの策定・公表そのものを一律に義務づけた規定はない」と説明する一方で、法定の利用目的の通知/公表、保有個人データの公表等が必要であるとしています。「プライバシーポリシーは法律で全事業者に義務」と書かないこと。

**2026年法改正の注意:** 令和8年改正法は **2026-07-17** に公布。個人情報保護委員会は、一部を除いて公布日から2年以内の政令で定める日から施行されると説明しています。一方、**2026-11-02施行版**の法令・規則等も公表されています。**公布済み=全規定が施行済みではありません。** 公開・更新日ごとに適用条文、施行日、規則、FAQと経過措置を確認し、未施行の将来要件を現在の義務と断定しないこと。16歳未満の取扱いなど特定規定への影響も確認する。

## 1. 事実の棚卸しを最初に行う

**文章を先に作らない。** 各案件で [data-inventory.template.md](data-inventory.template.md) を複製し、コード/設定/契約/運用への証跡を埋める。

必ず確認する例:
- 運営者の法的氏名/法人名称・住所・代表者氏名・連絡窓口（該当する公表事項）。
- 会員登録で取得する情報（Google `openid` / `email` / `profile` 等、実際のOAuth scopesとレスポンス）、匿名ユーザー識別子・ログイン時の引継ぎ。
- 利用者が入力するプロフィール、コメント、投稿、保存した楽曲/ライブ情報、連携アカウントID。
- Workersのリクエスト/セキュリティログ、D1のレコードとR2のオブジェクト、サポート記録、バックアップ等。**存在する前提にも存在しない前提にもせず検証。**
- GA4・Cloudflare Web Analyticsを実際に配信しているか、タグ/ビーコンのURL、Cookie/識別子、目的、送信先、収集期間。
- Spotify / Apple Music / YouTube / setlist.fm / MusicBrainz / DeezerとのAPI/埋め込み/アカウント連携。利用していないものはプライバシーポリシーに「利用中」と書かない。
- 取得源、利用目的、相手先（委託・第三者提供・共同利用を区別）、所在国・越境、保有期間、削除・開示等の対応手段。
- **UI表示だけでなくネットワーク通信とバックエンド実装を確認する。**

## 2. 推奨する公開文書の構成

以下は**章立ての推奨**であり、すべてが法令で一律に必須の見出しという意味ではありません。

| セクション | 記述ポイント | 作成・検証方法 |
| --- | --- | --- |
| 1 運営者・適用範囲 | 正式名、住所、代表者名（該当時）、適用サービス・Webドメイン | 事業者資料・契約・URLと一致 |
| 2 取得する情報 | 会員/ゲスト/端末・Cookie/閲覧履歴・問い合わせ・投稿・API由来 | データ取扱台帳のフィールドに連動 |
| 3 取得方法・利用目的 | 何のために、どこから、どの操作で取得するか | 目的を具体化、無関係な二次利用を含めない |
| 4 Cookie・解析・外部送信 | タグ、情報の種類、送信先、目的、選択/停止方法 | Network検証＋現行の規約/法の適用分析 |
| 5 共同利用・委託・第三者提供 | 各法的分類、受領者、提供目的、必要な同意/公表 | 事実/契約に基づき区別 |
| 6 外国にある第三者・越境 | 実際の移転先、条件、必要な同意と情報提供 | 国・提供先・例外・同等措置を法務レビュー |
| 7 保存期間・削除 | 種類別期間/決定基準、退会時・ログ・バックアップ等 | 実装・運用・法定保存と整合 |
| 8 安全管理措置 | 実際に講じた組織的・人的・技術的・物理的措置の概要 | 実装/手順と一致。機微な詳細は公開しない |
| 9 開示等・問い合わせ | 開示、訂正、利用停止等の手続、手数料があればその額、窓口 | 実際に対応可能な経路・本人確認を設計 |
| 10 利用者の設定・同意 | 必要な同意/停止/拒否、連携解除、Cookie設定 | 実UIの動作に一致 |
| 11 お子さま・対象地域（該当時） | 年齢に応じた取扱い、GDPR等の地域特有通知 | **該当する場合のみ**個別法務確認 |
| 12 改定・発効 | 制定/改定日、重要な変更時の通知、連絡先 | リリース管理と連動 |

### 日本法で検討すべき公表等

- 個人情報の**利用目的**を特定し、取得時の適用ルールに沿って通知・公表（個人情報保護法17条・21条等）。
- 保有個人データに関して、事業者の氏名/名称・住所・法人代表者名、利用目的、開示等の請求手続（手数料を定めたときはその額）、安全管理措置、苦情受付先など、法32条・施行令の該当項目を**本人の知り得る状態**に置く。必ず同一文書への全文記載が必要とは限らず、個別状況に応じた方法が認められる。
- 第三者提供・外国第三者提供、共同利用、要配慮個人情報、個人関連情報などは該当する場合に**別の要件**がある。第三者委託やプラットフォーム利用を一括して「第三者提供」と断定しない。
- 記載した「お問い合わせ先」には**実際の対応体制**が必要。自動生成した架空の住所・メール・会社名は公開禁止。

参考: https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/ と https://www.ppc.go.jp/personalinfo/faq/APPI_QA/

## 3. 記述ルール（GPT Work / Codex共通）

**PP-01 明確な日本語** — 読者が理解できる言葉を使う。略語は初出で説明し、専門用語を見出しだけにしない。何を、誰が、何のために、どこへ、いつまで、どう止められるかを具体的にする。

**PP-02 事実と予定を分ける** — 「保存しません」「第三者に提供しません」「自動削除します」「暗号化しています」「Cookieを使いません」等は**確認済みの場合のみ**。未実装の将来機能は利用中として記載しない。

**PP-03 機能と情報の対応** — 表で「収集項目 → 目的 → 保存先 → 提供/送信先 → 保持期間 → 操作/削除方法」を追えるようにする。すべての例示サービスを義務的に列挙しない。

**PP-04 義務と任意を区別** — 規格/法律/契約上の要件、推奨事項を分けて管理。通常のポリシー本文に断定的な法律意見を加えない。

**PP-05 利用目的は具体的** — 「サービス向上のため」だけの曖昧な説明に依存せず、例「ログインセッションを維持するため」「不正アクセスの検知のため」「使用状況を集計するため」のように実態へ即す。

**PP-06 正確な権利説明** — 取得したすべての情報が常に無条件で即時削除できると約束しない。適用法とデータ種別による権利・本人確認・法定例外を反映する。

**PP-07 既定の公開先** — 運用サイトに `/privacy` などの固定URL（案件で決定）を作り、通常はフッター、アカウント作成・ログイン画面、個人データの取得説明からリンク。直接URLからログインなしで読めることを確認。Google OAuth審査では公式の同一ドメイン要件も確認。

**PP-08 可読性・アクセシビリティ** — 短い段落、適切なH1/H2/H3、モバイルで読めるテーブル、本文の明瞭なリンク、印刷/拡大への対応。小さな文字や利用者の選択を妨げるUIにしない。

**PP-09 公開と変更管理** — 制定日・最終更新日・改定の実際の通知方法を記録し、サービス/取得データ/タグ/保存期間/外部委託先/適用法の変更時に再評価する。

**PP-10 運営者確認** — 公開文面は運営者・セキュリティ担当者、必要に応じて法務専門家が確認。AIは**ドラフト**を支援できるが適法性認定は行わない。

## 4. Cookie・アクセス解析・電気通信事業法の外部送信

1. 日本で**すべてのCookieに常に事前同意が必要という一律ルールではない**。サービス種類・送信情報・目的・相手先・対象利用者・対象法令を確認する。
2. 電気通信事業法の**外部送信規律**の対象となる役務・事業者であれば、所定の外部送信について、送られる情報、送信先、利用目的等を通知/公表等する必要があり得る。対象性・適用除外・対応方法（通知/公表/同意等）を個別に検討。
3. 「このサイトではCookieを使用しません」は、タグ・ログインセッション・埋め込み動画・アプリ内分析を調べるまで書かない。
4. **GA4** を利用する場合は利用とGoogleによるデータ収集/処理を説明し、Cookie・識別子、必要な同意、同意モードの実装（該当時）、広告関連機能の有無、収集するイベント/URLを確認。**Google Analyticsにメールアドレス等の個人識別情報を送信しない**。
5. **Cloudflare Web Analytics** は公式にプライバシー配慮型の解析サービスと説明されているが、導入しているbeacon等の実際の挙動を確認し、必要な外部送信の記載を検討。これだけでサイト全体がCookieなし/同意不要と断定しない。
6. Google AnalyticsとCloudflare Web Analyticsは**同じサービスではない**。データ/識別方法/利用目的/停止方法の差を分けて記述。
7. Webサイトにタグを追加したら、Networkを検証しデータ取扱台帳を更新してから公開文書も同期させる。

## 6. 共同利用・委託・第三者提供・外国提供を混同しない

- 「業務委託先にデータの保存/処理を依頼すること」と「個人データの第三者提供」は日本法上、同じとは限らない。取扱いの実態と法27条・28条、ガイドラインを照合。
- 海外にいる事業者・国外での処理が関係する場合、国名・提供先・本人の同意/例外/相当措置などを確認。**国外にサーバーが存在しそう**という推測だけで法的区分を確定しない。
- 共同利用を行う場合、共同利用者の範囲や目的、管理責任者等の該当公表事項を確認。
- 音楽APIの**公開メタデータ取得**と**利用者のアカウント連携**はデータの流れが異なる。必要な情報だけを記述。
- GDPR等の対象となる場合、法的根拠、期間、データ主体の権利、海外移転、監督機関への苦情等の追加の通知を個別に扱う。すべての日本サイトへEU項目を機械的に書かない。

## 7. 公開前チェック・変更時レビュー

[Privacy Review & Acceptance Checklist](../workflows/privacy-review.md) のPR-01〜PR-20に対応。

公開**不可**の例:
- 【要確認】/プレースホルダー/架空の運営者名や連絡先が残る。
- 実際にはGA4が動いているのに「解析を利用していない」と記述する。
- Googleログインで取得する情報/用途が説明されない。
- 本文がいう「退会で即時すべて削除」を実装で保証できない。
- D1/R2/外部APIの取り扱いが台帳と一致しない。
- 必須の通知/同意（該当時）を実装せず、ポリシー文面だけで代用している。
- 法令/契約の確認・公開責任者の承認がない。

**ライフサイクル:** 仕様変更 → データ棚卸し → 法令/契約確認 → ポリシー修正 → UX/実装確認 → 運営者承認 → 公開 → 改定履歴。重大な変更は変更前の通知や同意が必要か個別判定する。
